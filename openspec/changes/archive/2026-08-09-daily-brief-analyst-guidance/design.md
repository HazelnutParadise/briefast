## Context

Briefast 的報告版面寫死在 Go 程式，agent 只提供內容；報告以完整 JSON 存於 SQLite 的 reports 資料表，`internal/report` 負責 schema 驗證，`internal/site` 負責渲染。本 change 原本只改 skill 內容，討論後決定把「觀察重點」升級為正式欄位，讓版面能給它獨立的視覺處理、API 能強制驗證，因此擴及 Go 程式三個套件。

## Goals / Non-Goals

**Goals:**

- 觀察重點成為 report JSON 的正式欄位（`industries[].watch_md`、`stock_news[].watch_md`），API 驗證必填、版面獨立渲染。
- daily-brief skill 取得完整判讀指引：分析師視角、基本面時效紀律、固定四分類、台股範圍。

**Non-Goals:**

- 不加入收盤價、估值、目標價等需要價格或財報資料管線的內容。
- 不擴充美股、港股個股判讀。
- 不新增第五個動態產業區塊機制；若日後某子題長期霸佔傳產區塊再另案處理。
- 不改資料庫結構、不新增 migration（報告為 JSON 全量儲存與覆寫）。
- 不改既有五區塊版面順序，觀察重點只是產業與個股條目內的子區塊。

## Decisions

### watch_md 必填範圍

新報告的每個 `industries` 條目與每個 `stock_news` 條目都必須有非空白 `watch_md`，與既有「calls 條目必有 reason」的驗證哲學一致。捨棄「產業選填」方案：唯一產出端是 daily-brief skill，且分析師視角下每個區塊都寫得出至少一條可驗證的追蹤點，選填只會讓規則多一條分歧。歷史報告相容由渲染層處理，不靠放寬驗證。

### 觀察重點渲染方式

產業與個股條目在摘要內容之後渲染標示「觀察重點」的獨立子區塊，樣式由 Go 程式定義並遵循 DESIGN.md（零圓角、零陰影、規線只到大區塊）。不採 summary_md 尾段文字慣例：版面無法對 Markdown 內部片段做固定樣式，驗證層也無從把關。

### 蒐集完整性把關放在 skill 而非 API

來源可用性是執行期事實，API 收到 payload 時已無從判斷「這份報告是否因為來源掛掉而殘缺」——欄位全部合法的殘缺報告與正常淡日報告在 JSON 層無法區分。因此把關放在 skill 的蒐集與發布決策，而不是加 API 驗證規則。主來源與次要來源採不同處置：鉅亨網的文章已標注股票代號並附完整內文，是個股判讀的骨幹，失去它等於整份報告失去主要依據，必須停止發布；其餘來源屬補充覆蓋，缺一個仍能產出可用報告，照發但必須在執行回報揭露缺口，讓人得以判斷當日報告的涵蓋程度。

### 唯讀端點的驗證與記錄方式

`GET /api/report/{date}` 沿用 ingest 的 Bearer key 驗證，每次請求都從 SQLite 查 key 狀態，撤銷立即生效——報告內容在公開網站上本來就看得到，但用同一把 key 控管可避免多一套權限模型，也讓 key 撤銷同時斷掉讀寫兩條路。

update_log 的定位是報告更新軌跡，成功讀取不改變任何狀態，逐次記錄只會把管理後台的更新紀錄稀釋掉，因此不記；驗證失敗則記為 `read_rejected_auth`，與 ingest 的 401 一樣留痕，是撤銷生效與異常存取的觀測點。

### 同日重跑的覆寫防護

同日全量覆寫是既有且刻意的設計，不更動。風險在於覆寫沒有內容量的檢查：重跑若因來源暫時性失敗而抓得較少，會靜默取代先前完整版本。以「產業數或個股數少於已發布版本」作為觸發條件，因為它可由 agent 在送出前直接比對、無需額外資料，且能涵蓋來源失敗與判讀失準兩種退化情形。觸發時停下來說明差異並取得指示，而非自動放棄重跑——內容變少也可能是正確的（例如當日新聞確實稀少），該由人判斷。

### 歷史報告相容策略

欄位存在前入庫的報告沒有 `watch_md`，渲染遇到空缺直接省略子區塊，不顯示佔位文字、不報錯。驗證只作用於新的 POST，不回溯既有資料，因此不需要資料修補。

## Implementation Contract

- **資料形狀**：`internal/report` 的 Industry 型別與 StockNews 型別各新增字串欄位，JSON 名稱 `watch_md`，內容為 Markdown（1–2 條列點）。
- **驗證行為**：任一 `industries` 或 `stock_news` 條目的 `watch_md` 缺漏或僅空白時，`POST /api/report` 回 400，`errors` 陣列逐項列出違規條目，整份報告不落庫，update_log 記 rejected-schema——與既有驗證失敗行為一致。
- **渲染行為**：報告頁的產業區塊與個股詳情區塊，於每條目摘要後渲染「觀察重點」子區塊；`watch_md` 為空或不存在時該子區塊完全不出現。
- **驗收標準**：`go test ./...` 全綠，其中 internal/report 測試涵蓋缺欄位、空白字串、正常三種案例，internal/api 測試涵蓋缺 watch_md 回 400 且不落庫，internal/site 測試涵蓋有無 watch_md 兩種報告的渲染結果。
- **唯讀端點契約**：`GET /api/report/{date}`，`date` 為 `YYYY-MM-DD`。帶有效 Bearer key 且該日有報告時回 200 與該報告的完整 JSON（與 POST 時送入的結構相同）；key 缺漏、無效或已撤銷回 401 並記 `read_rejected_auth`；`date` 格式不合法回 400；該日無報告回 404。以上皆回 `ok=false` 與 `errors` 陣列，與 ingest 的錯誤形狀一致。成功讀取不寫 update_log。
- **發布把關行為**：蒐集階段對每個來源記錄成敗；失敗來源先重試一次。鉅亨網重試後仍失敗時，agent 停止流程、不組稿也不 POST，並回報失敗來源與原因。次要來源失敗時照常發布，並在執行回報列出缺漏來源。送出前若該日期已有報告，比對產業數與個股數，任一少於既有版本就停下來說明差異原因並等待指示，不得逕行 POST。
- **把關驗收標準**：以內容審查確認 SKILL.md 同時具備來源成敗記錄、重試、主／次來源分流處置、缺漏揭露、同日重跑數量比對五個要素，且與既有 HTTP status 處理規則無矛盾。
- **範圍邊界**：in scope——上述欄位、驗證、渲染、SKILL.md 內容與發布把關規則；out of scope——資料庫 schema、admin 後台、歷史資料回填、版面五區塊結構，以及任何以程式強制執行蒐集完整性的 API 驗證。

## Risks / Trade-offs

- [API 開始拒絕缺 watch_md 的報告，若 skill 更新與部署不同步會造成發布失敗] → 同一 change 內同步改 SKILL.md 與程式，一起部署；skill 的送出前檢查清單同步加上 watch_md 檢核。
- [執行模型為滿足必填而硬湊空泛觀察點] → skill 明文要求觀察點必須連結該條目引用的新聞或基本面，禁止範本化句子。
- [四分類邊界誤判（如生技歸傳產不直覺）] → SKILL.md 附涵蓋邊界表與指派範例，封閉分類保證至少不會漏列。
