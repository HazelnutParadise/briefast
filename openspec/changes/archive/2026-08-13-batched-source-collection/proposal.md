## Summary

蒐集階段從單一籠統步驟改為四個具名批次，每批各自宣告抓哪些端點並交出取得筆數，四批的彙整表成為進入判讀的前置條件。

## Motivation

現行 skill 把蒐集寫成一個動作：列出六個來源的端點，要求「逐一記錄每個來源這次是成功還是失敗」。這種敘述性要求對執行模型的約束力很弱，因為它沒有中間產出——模型可以只抓主來源就進入判讀，而報告裡看不出差別。

關鍵缺口在於「沒抓」與「沒提」無法區分。既有的來源成敗把關只處理「失敗」，而未曾嘗試的來源根本不會進入失敗狀態，靜默略過不留任何痕跡。

把蒐集拆成具名批次可以改變這件事：每批明確宣告抓哪些端點，並在進入下一批前寫下該批的取得筆數。略過一個來源因此從「少做一個模糊動作」變成「交不出某一批的數字」，是一個顯而易見的缺口而不是無聲的省略。

## Proposed Solution

- 蒐集章節改寫為四個具名批次，彼此可平行執行，每批列出該批負責的端點與必須產出的計數：
  - 批次 1 鉅亨網六個分類 API：各分類取得幾則、其中未讀幾則。
  - 批次 2 證交所兩個資料集：各資料集落在時間窗口內幾筆，遵守既有序列與間隔規則。
  - 批次 3 工商時報六個分類 RSS：各分類未讀幾則。
  - 批次 4 中央社、科技新報、自由時報三個 feed：各站未讀幾則。
- 四批針對不同主機，可同時發出；證交所批次內部仍維持序列與間隔規則，因為該限制是對主機而非對批次。主來源失敗仍中止整個流程，只是在平行回合結束後才判定。
- 四批全部回報後彙整成一張涵蓋所有來源的表，該表是進入判讀的前置條件；表不完整就不得開始判讀。計數的關卡在判讀之前，而不在批次之間。
- 移除鉅亨網失敗即整份不發的規則。改成平行後「主來源失敗就不抓其他」已不可行——判定時其餘三批早已抓完；而重新檢視也發現該規則過嚴：證交所重大訊息本身帶公司代號、月營收是硬事實，工商時報與中央社等也涵蓋台股，缺 cnyes 損失的是覆蓋密度與便利性，不是報告的可行性。改為所有來源失敗都走同一套處理：照常發布，缺漏只列在執行回報。缺漏與蒐集機制一律不進報告內容——把來源清單、批次結構或當日缺了誰寫進 `overview_md`，等於對外公開我們的蒐集方式與覆蓋弱點。個別文章的 `sources` 引用不受影響。
- 送出前檢查清單改為引用這張彙整表，而不是只確認「成敗已記錄」。

## Non-Goals

- 不改來源端點清單本身。
- 不改報告 JSON 結構，蒐集彙整表留在執行回報，不進 payload。
- 不新增 API 驗證或後台稽核機制；那屬於上線後依實際表現再評估的範圍。
- 不改去重流程與 seen.py 的用法。
- 不強制平行執行，也不規定並行實作方式；證交所以外的批次不新增速率限制。
